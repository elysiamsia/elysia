> 2026-10-18 起草。触发：主人提出「整个项目搬到服务器后想重构，充分利用好服务器」，同时正在准备 13 英桀 Q 版小人素材。
> 状态：**方案待拍板**，本文档不含代码改动。

## 二、真实技术债（按痛感排序，都是这半个月亲身踩的）

### 1. 13 个角色页是复制粘贴出来的（最痛）

同一套结构、样式、脚本被复制了 12~13 份。真实代价：

- 加「刻印水印」要改 **12 页**；
- 修「触控目标 44px」要改 **12 页**；
- 清「毛玻璃」要扫 **12 页**；
- 每次改完都要重新验证 12 遍（这半个月我为同一件事反复跑了十几轮）。

**结论：这是本项目最大的一笔债，也是重构最该解决的事。**

### 2. 数据散落在各页内联 <script> 里

角色信息（生日、刻印名、12 个探索点文案、游戏配置、语录）都写在各页的 `var THEME = {...}` 里。
想「一次改全部」（比如统一调整探索点数量、或给每个人换 Q 版小人）就必须逐页改。

### 3. 素材管线是手工的

webp 转换、512/256 多尺寸、签名图，全是我临时写 Pillow 脚本跑的（`tmp/*.py`）。
Q 版小人进来后，如果每人 3~5 个尺寸 / 2 个用途，手工会不可维护。

### 4. 后端很薄，且是手写路由

`server.js` 用 `node:http` 手写：路由靠 `if (url.pathname === ...)`、校验靠人肉、JSON 文件落盘靠 `load/save`。
功能能跑（已实测），但**加第三个功能就会开始互相污染**（擂台进来时已经出现：DB 缺表导致服务崩溃）。

### 5. 没有构建步骤 ⇒ 无法"改一处、全站生效"

## 三、重构目标（明确"做什么"，更要明确"不做什么"）

### ✅ 要做

| # | 目标 | 收益 |
|---|---|---|
| A | **单一数据源**：13 个角色抽成 `content/` 下的 JSON | 改数据一次生效；Q 版小人可挂到数据上 |
| B | **模板化**：抽出共用骨架（head/开场/底部/探索/游戏槽） | 改一处全站生效，13 页不再手改 |
| C | **保留静态输出**：build 出与现在同构的 HTML | 首屏/SEO/缓存全部不退化 |
| D | **素材管线**：sharp 自动多尺寸 webp | Q 版小人可批量接入 |
| E | **后端分层**：Fastify + SQLite + 路由模块 | 加功能不再互相污染 |
| F | **统一后台**：内容/留言/素材/数据 | 不用再找我改代码 |
| G | **部署升级**：build → 原子发布 → 健康检查 → 秒回滚 | 已有雏形，补齐 |

### ❌ 明确**不做**（防止过度工程）

| 不做 | 理由 |
|---|---|
| **不换 React/Vue 做 SPA** | 会毁掉现在的首屏速度、SEO 与那些手工调过的入场动画；这个站是**内容站**，不是应用 |
| **不上 Docker/K8s** | 2 核 2G 单机，容器只会增加内存开销与排障成本 |
| **不上 Redis / Postgres** | SQLite 完全够（留言、押注、金币的量级）；少一个进程就少一份内存和运维 |
| **不引入重型 admin 框架** | 后台页面自写服务端渲染即可，几十 KB 的事 |
| **不改现有视觉** | 毛玻璃清理、44px 触控、刻印水印、克制的暗色美学 —— 这些是打磨过的成果，不是重构对象 |

## 四、技术选型（附理由，都按 2 核 2G 校准）

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Node 22**（已装） | 不新增依赖面 |
| HTTP 框架 | **Fastify** | 比 Express 快、内置 JSON Schema 校验（正好用来校验 API 入参）、内存友好 |
| 模板 | **Nunjucks** | 语法直观、无客户端运行时、与现有 HTML 结构亲和度最高 |
| 生成 | **自写 build 脚本**（Nunjucks + content JSON → HTML） | 不引入 11ty 的目录约定，避免与现有结构打架；生成逻辑完全可控、可逐页 diff |
| 数据库 | **better-sqlite3** | 同步 API、无连接池、单文件可备份；2G 内存友好 |
| 图片 | **sharp**（libvips） | 比 Pillow 快、内存可控（可限制并发） |
| 进程管理 | **systemd**（已用） | 不引入 pm2，少一层 |

> ⚠ **一个关键取舍要拍板**：引入构建步骤后，"改一个字的文案"也要 `npm run build`。
> 但换来的是"改一处、全站生效"。**这正是现在的痛。**

## 五、分阶段计划（每阶段可独立验收，线上不中断）

| 阶段 | 产出 | 验收标准 |
|---|---|---|
| **0 · 地基** | 目录结构（`content/ templates/ src/ build/ public/`）+ Fastify 骨架 + SQLite 建表迁移 | 新架构能跑起来，但**线上仍是旧站**（新站在 8443 旁路） |
| **1 · 抽数据 + 模板化** | 13 角色 JSON + 共用模板 + 生成器 | ⭐ **逐字节 diff**：生成的页面与现网页面结构一致（差异必须逐条解释清楚） |
| **2 · 素材管线** | sharp 多尺寸 + Q 版小人接入 | 每人一套尺寸产出、体积达标；**手机端实测**（320/360/390） |
| **3 · 后台** | 内容编辑 / 留言审核 / 素材上传（服务端渲染） | 不登录看不到；能改一处内容并全站生效 |
| **4 · 擂台前端** | 赛程 / 押注 / 回放 / 双榜 + 匿名本地模式 | 真机走一遍完整流程（签到→押注→结算→回放） |
| **5 · 切换与观测** | 灰度切流、健康检查、日志、备份、回滚演练 | 备案通过后切域名；**回滚演练必须真的跑一遍** |

**顺序说明**：阶段 1 是最重的一步，但它解决的是最大的债；阶段 2 依赖你 Q 版小人的规格；
阶段 4 可以并行（它只加页面，不改现有结构）。

## 六、红线（重构期间必须守住）

1. **线上不中断**：新架构全程跑在旁路端口，验证通过才切；旧站保留可回滚。
2. **不能"看起来差不多"**：阶段 1 必须拿出**逐字节/逐元素 diff**，差异逐条解释。这是硬要求。
3. **现有断言必须全绿**：探索 29 条、游戏 4 条、健康检查、aria、减动偏好 —— 重构后一个都不能掉。
4. **手机端不可退化**：文档宽 = 视口宽、触控 ≥44px、无横向溢出（这三条是这半个月修出来的，已固化）。
5. **防剧透不变**：擂台战报永远只能经后端时间闸门取。
6. **每一步可回滚**：`deploy.sh rollback` 的能力要延续到新架构。

## 七、Q 版小人素材规范（阶段 2 的输入，需要主人确认）

建议规范（**先定规范，再收素材**，否则会返工）：

| 项 | 建议值 | 说明 |
|---|---|---|
| 画面 | **透明底 PNG**，1:1 或 3:4 | Q 版小人通常要立在各处，透明底是刚需 |
| 逻辑尺寸 | 源图 ≥ **1024px**（长边） | 之后由 sharp 自动降采样 |
| 命名 | `{角色key}-chibi.png`（如 `kevin-chibi.png`） | 角色 key 与 JSON 里一致（kevin/eden/aponia/villv/kalpas/su/sakura/kosma/mobius/griseo/hua/pardofelis/elysia） |
| 用途 | ① 角色页浮标 ② 擂台选手卡 ③ 首页总览 | 用途决定输出尺寸，先定用途再切图 |
| 输出 | 自动生成 `@1x/@2x` + `webp` | 目标：单张 ≤60KB（手机端收益最大） |
